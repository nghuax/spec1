01 / OVERVIEW

One shell. Four independent systems.

HEAL is a static, framework-free site. Six public HTML documents provide accessible shells; three JavaScript modules insert shared content and navigation; CSS defines the campaign identity; four local p5.js packages run inside same-origin iframes.

WEBSITE SHELL

Renderer-driven pages

The HTML contains semantic mounting points rather than duplicated page content. site.js reads body data attributes and renders the correct page into those mounts.

CONTENT MODEL

One source of truth

Project text, chapter order, iframe paths and controls live in content.js. Navigation, home panels and work pages all consume the same objects.

ARTWORK BOUNDARY

Isolated canvases

Each artwork owns its p5 runtime, canvas, interaction state and local stylesheet. An iframe prevents sketch globals such as setup() and draw() from colliding.

!

No compilation happens. The browser loads the committed HTML, CSS, ES modules, font and p5 files directly. This makes the repository itself the deployable artifact, but it also means paths and filename case must remain correct.

02 / ARCHITECTURE

What happens after a URL opens.

The browser follows a short deterministic chain. Content is centralized, layout is generated once, and continuous animation stays confined to the chosen artwork frame.

→
site.jsCalls all render functions; only the matching mount exists.
→
content.jsSupplies project and chapter data.
→
Generated DOMNavigation, page content, footer and iframe are inserted.

Parse

The page loads shared CSS and the module entry point.

Identify

data-page, data-root and data-chapter establish context.

Render

Header, footer and exactly one page body are generated.

Run artwork

The iframe loads its own p5 library and sketch loop.

Path rule

Top-level pages use data-root="."; work pages use data-root="..". The helper route(root, target) then builds links that work both locally and under GitHub Pages' /spec1/ project path.

Progressive enhancement

The static shells retain titles, descriptions, landmarks and skip links before JavaScript runs. The detailed content requires modules, so the site is intentionally served over HTTP rather than opened through file://.

05 / CSS

The visual system is layered.

Six shared stylesheets move from universal foundations to page-specific composition. Cascade order is intentional: tokens and reset load first, common site rules next, then home or artwork-page rules.

css/fonts.css

Typeface registration

Registers the local WOFF2 as a variable font with weights 200–700 and font-display: swap.

css/variables.css

Design tokens

Defines the eight-colour HEAL palette, fluid spacing, page gutter, header height, border rule and transition curves.

css/reset.css

Predictable defaults

Normalizes box sizing and margins, applies Stack Sans Notch system-wide, supplies focus/selection rules, and neutralizes motion when requested.

css/site.css

Shared layout

Sets chapter-specific themes via body attributes, styles navigation/footer, and contains the complete About page system and responsive menu.

css/home.css

Homepage composition

Controls the giant HEAL word, poster-like type field, chapter colour panels, geometric hover responses and small/landscape adaptations.

css/artwork.css

Work-page composition

Styles chapter mastheads, progress state, 16:9 iframe, loader/error layers, interaction instructions and adjacent navigation.

body[data-chapter='harm'] {

Responsive strategy

clamp() provides fluid type and spacing. Major layout changes happen near 840px; tighter adjustments occur around 520–580px; a short landscape query protects artwork controls on shallow screens.

Graphic strategy

Oversized text, hard borders, pseudo-elements and transformed rectangles create the poster aesthetic without image assets. The only shared visual binary is the font.

06 / ARTWORK 01

H

HARM

Coal creates electricity and architecture, but every burn adds persistent environmental debt. This is the largest and most simulation-heavy sketch.

Demand

Hovering a completed house or factory for 0.45 seconds creates an orange demand signal.

Coal

Clicking coal—or dropping it into the hopper—fractures it into pieces travelling on quadratic curves.

Combustion

The leader fragment triggers power, unlocks architecture and emits smoke, carbon and ash.

Consequence

Particles deposit into a diffusing pollution grid that damages local objects and thickens the atmosphere.

burn → useful power + architecture + 3.8 × overdrive multiplier pollution

State and update pipeline

WORLD STATE

houses, trees, poles, factories and demandNodes describe the built environment. Architecture starts locked and is released through five curated ARCHITECTURE_WAVES.

TRANSIENT STATE

coal, fragments, demandSignals, energyClusters, smoke, carbonDust, ash and debris are capped particle collections.

ENVIRONMENT STATE

An 18 × 10 pair of grids stores local pollution. Deposits diffuse to neighbours, decay slowly, receive upward bias and can be sampled by position or column.

GLOBAL STATE

pollution, smokeCeiling, machineHeat, overdrive and recent burnTimes connect individual actions to the full composition.

08 / ARTWORK 03

A

ADAPT

Sun and wind are complementary tools. Neither charge alone fully restores a module; recovery depends mostly on the lower of the two.

adapt/sketch.js — the central recovery rule
function moduleRecovery(m) {
  const dual = min(m.sun, m.wind);
  return constrain(dual * 0.84 + (m.sun + m.wind) * 0.08, 0, 1);
}

84% of recovery comes from the weaker shared charge. The remaining 16% comes from total sun plus wind. This encodes the concept that balanced systems outperform a single intervention.

MODULE FIELD

46–58 modules

Houses, trees, flowers, factories, farms, stores, bushes and gardens are distributed with collision-aware spacing and kind-specific mass.

SUN TOOL

Charge + burst

Dragging adds sun charge inside a 248px falloff radius and creates expanding blue/lime rings.

WIND TOOL

Charge + force

Dragging adds wind charge inside 274px, pushes modules based on inverse mass and accelerates nearby smoke away.

10 / INTEGRATION

Isolation without visual separation.

Why iframes?

Every p5 package defines global callbacks named setup, draw, keyPressed and windowResized. Loading four sketches into the parent page would overwrite globals. Separate documents provide separate JavaScript realms and CSS scope.

Why same-origin?

All artwork assets live inside the repository. Relative URLs remain portable, no third-party network is required, and browser security does not block the parent page from loading the frames.

Shared typography

Each artwork entry imports ../../css/fonts.css; each sketch also calls textFont('Stack Sans Notch'). DOM labels and canvas text therefore use the same self-hosted variable font.

Shared narrative

The iframe never owns chapter headings or long instructions. Those stay in the parent page, where they remain selectable, responsive and accessible even though the primary visual is a canvas.

Accessibility mechanisms

MechanismImplementation
Landmarks and titlesEvery route has language, title, description, header/main/footer landmarks and one meaningful H1 after rendering.
Keyboard navigationVisible focus styling, semantic links/buttons, Escape-to-close mobile menu and keyboard artwork shortcuts.
Artwork descriptionsIframe titles plus hidden descriptions/instructions connect the visual experiences to explanatory text.
Loading feedbackThe loader uses role="status"; HARM has an aria-live="polite" instruction/status element.
Reduced motionCSS minimizes transitions/animations and JavaScript skips scroll-reveal observation.
Responsive accessFlexible type/spacing and aspect-ratio wrappers protect reading order and interaction surfaces across widths.
△

Known boundary: most p5 interactions are pointer-led and canvas pixels do not expose rich semantic object trees. The parent instructions and keyboard reset/tool shortcuts reduce this limitation, while EXHAUST additionally overlays a real accessible button.

11 / DEPLOYMENT

GitHub Pages receives the code folder.

The workflow is intentionally short because there is nothing to compile. Every push to main checks out the repository, configures Pages, packages ./code and deploys that artifact.

.github/workflows/deploy-pages.yml
permissions:
  contents: read
  pages: write
  id-token: write

steps:
  - uses: actions/checkout@v6
  - uses: actions/configure-pages@v5
  - uses: actions/upload-pages-artifact@v4
    with:
      path: ./code
  - uses: actions/deploy-pages@v4

Permissions

Repository content is read-only to the job; Pages and OIDC permissions allow the official deployment action to publish.

Concurrency

The pages group avoids overlapping deployments, while cancel-in-progress: false lets an active release finish safely.

Manual recovery

workflow_dispatch exposes a Run workflow control when a deployment must be repeated without changing source.

13 / MAINTENANCE

Where future changes belong.

Change wording

Edit js/content.js. Keep shared chapter titles, statements, descriptions and instructions out of individual HTML shells.

Change site colours

Edit palette tokens in css/variables.css, then verify chapter overrides in css/site.css and hard-coded artwork palettes separately.

Change navigation

Edit js/navigation.js. Preserve aria-current, Escape handling and root-relative routing.

Change a simulation

Edit only that artwork's sketch.js. Test it standalone and through its iframe because pointer coordinates and resize behaviour differ.

Add final credits

Populate the intentionally empty fields in siteContent.project and each chapter's credit. Conditional rendering will expose them automatically.

Release changes

Serve code/ over HTTP, test all routes and artworks, commit, then push to main. GitHub Pages deploys the same folder.

✓

Recommended verification: check browser console errors, keyboard focus, mobile menu, iframe load/error states, every artwork's reset control, all relative asset URLs, and reduced-motion mode before submission.
